# PRD 6.2 — Upload hardening + author alt text

**Status:** drafted 2026-11-03 (D-86), awaiting Shane's review; nothing built. Governed by D-59 (Phase 6 = readability + uploads), D-40/D-51 (uploads through a guarded route handler, local disk, one seam), D-31 (signals for humans) and rule 8 (fixtures frozen; this PRD asks for one regeneration). Size M, one PR. Builds on `phase-6.2` off `phase-6.1b` (PRs #5–#8 still open).

## Problem

Uploads (task 4.7) shipped with type, size and magic-byte checks. The 2026-10-29 reviews (a11y S3/S5, SME #10, PO §B6) and a re-read of the code for this draft found these gaps:

1. **No author alt.** `p/[post]/page.tsx:196` renders `alt="Attachment 1a2b3c4d (image/png, 312 kB)"`. The attach form has no description field, so a screen reader hears an id and a size (WCAG 1.1.1).
2. **Pixel flood.** `checkUpload` (`src/forum/uploads.ts`) reads 8 magic bytes and the byte count. A 2 MB PNG can declare 10⁴ × 10⁴ px. Nothing on the server decodes today, so the cost falls on every member's browser that opens the thread, and on any thumbnailer behind the D-51 seam later.
3. **No upload window, no per-post count.** `upload` is not one of the `ACTIONS` in `src/rules/index.ts`, so `guardAndRecord` never sees it. One author can attach any number of 2 MB files to one post. Local disk is the only ceiling.
4. **Found while drafting: the upload route skips the door.** `POST /o/[org]/f/uploads` calls `requireOrg` and then `storeUpload` directly. Neither calls `admit`, so a **banned member can still attach files to their own post** (D-14 says a ban stops new writes), and a **locked thread still takes attachments** (`lock_refuses` covers reply, vote and edit). The route also catches only `ForumRefused`: once a window exists, a `RateLimited` refusal would become a 500. None of this has been reproduced yet; the first red tests below are the reproduction (rule 7).
5. **Uploads of removed posts are still served.** The `[id]` route never reads the post's status. The thread page also lists `post.uploads` to every member when the post is `removed` or `deleted`, even though the body is hidden.
6. **EXIF is kept.** A homelab photo's GPS tag is a home address. The SME row asked for EXIF to be stripped; the phase list deferred it as "needs an image library". It does not need one (decision 4).

**Already closed, not in scope:** the refusal inside a closed `<details>` (a11y S3, PO A6) was fixed in 4.1.6. The `<p role="alert">` now sits above the panel and the panel opens on `?upload=`. The e2e `4.1.6` spec pins this. The one remaining piece of S3, `aria-describedby` from the file input to the message, is in scope here.

## Scope

- **Fixture first (rule 7).** `tools/uploadlib.py` (oracle: header parse and verdict, stdlib `struct` only) and `tools/build_upload_fixtures.py --seed 20261103` → `fixtures/uploads/cases.json`. The fixture holds header-only byte strings as hex, a few hundred bytes each, and no real images. Each case gets the oracle's `{width, height, verdict, code}`. The file is hashed in the manifest. Cases:
  - PNG: 1×1 allowed; 20 000 × 20 000 refused; IHDR not the first chunk refused; a truncated IHDR refused.
  - JPEG: SOF0 4000 × 3000 allowed; SOF2 (progressive) over the cap refused; an SOF after a 64 KB APP1 found; DQT/DHT before the SOF; no SOF before the scan refused; two SOFs refused.
  - WebP: VP8 (lossy, 14-bit fields), VP8L (lossless, 14-bit packed), VP8X (24-bit canvas) at, above and below the cap.
  - Any type: zero width or height refused.
  - With decision 4, the strip cases too.

  `engine:eval` reads the file, and `fixtures:check` covers it.
- **Header parse, pure.** `src/limits/image-header.ts` returns `{ width, height } | refusal` from the bytes the route already holds. It is pure, so `engine:lint` covers it, and it adds no dependency. `checkUpload` refuses `INPUT_INVALID` with `upload is W × H px (N pixels); the limit is M` when `width × height > upload.max_pixels`.
  - **Ceiling, stated in the code (`ponytail:`):** the cap applies to the dimensions the header claims. A decoder that disagrees with its own header, and APNG frames, are not modelled. APNG frames are bounded by the canvas by spec, but that is not checked.
- **Rules as data.** In `rules/limits.json`: `upload.max_pixels` and `upload.max_per_post`, plus an `upload` entry in `windows`. `"upload"` joins `ACTIONS`; the schema already requires a window for every action. `LimitHit.action` is a `String`, so no migration is needed. Each new constant gets a golden case:
  - **GL-15..GL-17:** the young upload window (2 allowed, the third refused, retryAfter).
  - **GL-18:** the regular window.
  - **GL-19/20:** `max_per_post` at the count and over it.
  - **GL-21/22:** `max_pixels` at the cap and one pixel over.

  The golden cases are indexed in `docs/domain-brief.md` §3a.
- **`expected_limits.csv` gains one row**, written by the oracle before any TypeScript (rule 8 regeneration, D- entry): `spam-young-uploads` replays u193 with 30 attempts at one per 10 s through `limitslib.replay`. The six existing rows must come out byte-identical. There is no `normal-*-uploads` row, because the frozen community fixture has no uploads. That check is vacuous by construction and is stated as a caveat, not faked. `abuse:spam` replays the same script through the live store, and its count must equal the row.
- **The upload path goes through the door.** `storeUpload` runs, in the door's order:
  1. `admit` (ban);
  2. post exists and you are its author;
  3. `refuseIfLocked(…, 'upload')`;
  4. the per-post count;
  5. `checkUpload` (type, size, magic bytes, dimensions);
  6. `guardAndRecord('upload')`, last, so a refused file records no hit;
  7. the write.

  The route catches `RateLimited` as well as `ForumRefused` and renders both as `?upload=<message> (CODE)`, with `retryAfter` in the message.
- **Author alt.** Migration: `Upload.alt String?`, with three states:
  - `null`: a legacy row. It renders `alt="Undescribed attachment"`, and the author sees "add a description".
  - `''`: decorative. It renders `alt=""`, and the author has to tick it explicitly.
  - text: rendered as the `alt` attribute, which React encodes.

  The form gets `<label>Describe the image <input name="alt" maxLength={300} aria-describedby=…></label>` and a `Decorative (no description)` checkbox. The field is refused `INPUT_INVALID` when it is empty without the checkbox, longer than 300 characters, or contains control characters; the last check reuses `checkText`, the same one that refuses X-37's NUL. The file input also gets `aria-describedby` pointing at the refusal.
- **Removed posts.** The `[id]` route returns 404 for an upload whose post is not `visible`, except to moderators. Moderators see a removed body today (P0-6), and the attachment is evidence for the same review. The thread page lists attachments only where the body is shown.

## Non-goals

- An image library or decoder, thumbnails, re-encoding or format conversion (ask-before-add; D-51 names the seam).
- Moving files off local disk. Deleting the bytes of a removed post's upload (a 404 hides them, the bytes stay for appeal and review, the same as a removed body).
- Uploads on comments. Any change to `src/render/`: `xss:check` must stay 61/61 and byte-identical.
- A malware scan or a content classifier.

## Acceptance

- **Fixture and engine:** `fixtures/uploads/cases.json` and the new `expected_limits.csv` row exist before `src/limits/image-header.ts`. `engine:eval` reports the upload cases with 0 differences. `ranking:golden` ends `OK` with GL-15..GL-22. `fixtures:check` is OK, with the manifest regenerated and the six existing limit rows byte-identical. `engine:lint` is OK with the new file.
- **Integration (`tests/integration/uploads.test.ts`), each red first:**
  - A banned member's upload is refused `BANNED_UNTIL`.
  - An upload to a locked thread is refused `THREAD_LOCKED`.
  - The `max_per_post + 1`-th upload is refused.
  - A young member's third upload in the window is refused `RATE_LIMITED` with retryAfter, and the refused attempt records no `LimitHit`.
  - A 20 000 × 20 000 PNG header is refused.
  - A removed post's upload returns 404 to a member and 200 to a moderator.
  - Alt: an empty field is refused, decorative is accepted, 301 characters are refused, a NUL is refused.
- **e2e, failing first:**
  - An attachment's accessible name is the author's description.
  - A decorative one has `alt=""`.
  - Submitting without a description shows the refusal above the panel, and the file input's `aria-describedby` names it.
  - A stored description of `"><img src=x onerror=…>` renders as attribute text: the DOM has no second `img` and no `onerror` attribute.
  - axe 0 at 320 / 768 / 1280, light and dark, on a thread with an attachment.
- `npm test`, harness 14/14 (uploads stay a route handler, D-51), full Playwright and `foundation:drift` green in CI.

## Decisions this PRD asks of Shane (at review)

1. **Thresholds:** an `upload` window of 10 per hour (young: 2), `max_per_post` 4, and `max_pixels` 25 000 000 (25 MP; a 6000 × 4000 phone photo is 24 MP). Or other numbers. **Rec: as proposed.** The study cannot calibrate them because the fixture has no uploads, so they are policy, stated as such in the D- entry.
2. **A lock refuses `upload`** (`"upload"` added to `rules/moderation.json` `lock_refuses`), or attaching stays open on a locked thread. **Rec: refuse.** Attaching changes the post the same way an edit does, and edit is already refused.
3. **Attachments of removed posts: 404 to members, still served to moderators**, or 404 to everyone. **Rec: moderators keep them.** It matches how a removed body is handled (P0-6), and a moderator reviewing a report needs the image.
4. **EXIF and GPS:** (a) **strip metadata at the container level**, with no decoder and about 60 lines on the same byte walk as the dimension parse: JPEG APP1 (Exif, XMP) segments, PNG `eXIf`/`tEXt`/`iTXt`/`zTXt` chunks, WebP `EXIF`/`XMP ` chunks with their VP8X flags cleared. `sha256` would be of the stored, stripped bytes, and the strip cases would be added to the fixture. (b) Keep it deferred and add a line to the attach form: "Photos can carry your location; remove it before uploading." **Rec: (a).** It is the worst harm in SME #10 (a home address), it needs no dependency, and the phase list only deferred it on the belief that it needed a decoder. Choosing (a) amends the 6.2 row's "must not" through D-86.
