# PRD 5.2 — Ring and aged-brigade signals as data

**Status:** approved 2026-11-01 as written (D-75); `min_contribution_chars` deferred. Governed by D-31 (signals for humans, never automatic action), D-59 (Phase 5 scope), D-73 (thresholds come from this PRD's own fixtures, not the frozen community fixture).

## Problem

The only vote detector today is D-31's: ≥ 5 *gated* downvotes on one node inside 600 s → one `BRIGADE` item (`rules/limits.json` `signals.brigade`, made data in 4.1.3). It watches exactly the votes the counter already refused. Two techniques get through with nothing in the queue (SME review, `docs/reviews/2026-10-29-sme.md` #1, #2):

1. **Upvote ring.** Only downvotes are gated (`src/limits` `downvoteAllowed`); a minutes-old account may upvote 10 times a minute. Ten fresh upvotes add log10(10) = 1 to a post's hot score — 12.5 h of age at gravity 45,000 s — and every one is counted.
2. **Aged brigade.** The gate is 24 h **and** 3 contributions. Accounts that wait a day and post three short replies pass it; their downvotes are `APPLIED`, counted, and never examined. Seven such accounts take a post to net −6 silently.

PRD 5.3 showed the frozen fixture cannot set thresholds for either (no aged sockpuppets; D-73), so this PRD brings its own.

## Scope

### Rules (data, closed schema)

Extend `rules/limits.json` `signals` (the zod schema stays closed; unknown keys refused by name):

```json
"signals": {
  "brigade":      { "min_voters": 5, "window_seconds": 600 },
  "ring":         { "min_voters": 6, "window_seconds": 600 },
  "aged_brigade": { "min_voters": 5, "window_seconds": 600, "max_account_age_days": 7 }
}
```

- **RING:** ≥ `min_voters` distinct **young** accounts (L-1, the existing `young_account` rule: < 24 h or < 5 contributions) whose upvote on one node was `APPLIED` inside `window_seconds`.
- **AGED_BRIGADE:** ≥ `min_voters` distinct accounts that **passed** the downvote gate but are younger than `max_account_age_days`, whose downvote on one node was `APPLIED` inside `window_seconds`.
- Proposed values mirror D-31's shape (same window; ring threshold one higher because upvotes are the common action) and are set by the scenario fixtures below, each with a golden case. Shane may change them at review.

### A pure detector

`src/votes/signals.ts`: `detectSignals(events, accounts, rules) → Signal[]` over vote events with their outcomes — pure (D-7: `now` is a parameter; `engine:lint` covers it). One signal per (kind, node, window); a later qualifying event in the same window updates the voter count, not a second row (the D-31 behaviour, generalised). The existing gated-brigade check moves into the same function so all three kinds share one definition.

### Fixtures first (rule 7), without touching the frozen community

A separate, additive fixture set, so the 12 expected files stay byte-identical (rule 8; D-61 precedent):

- `tools/build_signal_fixtures.py --seed 20261101` → `fixtures/signals/scenarios.json`: small self-contained scenarios, each a handful of accounts, one node, timestamped events.
- `tools/signallib.py` (oracle, stdlib) → `fixtures/signals/expected_signals.csv` (`scenario, kind, node, voters, window_start`); both hashed into `MANIFEST.json`.

| Scenario | Setup | Expected |
|---|---|---|
| S-RING | 8 accounts 2 h old upvote one post within 300 s | 1 `RING`, voters 8 |
| S-RING-SLOW | the same 8 upvotes spread over 3 h | none |
| S-RING-MIXED | 4 young + 10 mature accounts upvote within 300 s | none |
| S-RING-EDGE | exactly `min_voters` young upvotes, the last at `window_seconds` − 1 / + 0 | 1 / none |
| S-AGED | 7 accounts 3–6 days old, 3 one-line replies each, downvote one post within 600 s | 1 `AGED_BRIGADE`, voters 7 |
| S-AGED-ORGANIC | 7 accounts 30+ days old downvote within 600 s | none |
| S-GATED | the existing 7 gated downvotes (D-31) | 1 `BRIGADE`, voters 7 (unchanged) |
| S-BOTH | a ring and an aged brigade on the same node | 1 of each; not merged |

Golden cases GS-01..GS-08 in `tools/golden_answers.py`, one per scenario.

### Wiring

- **Schema:** `BrigadeSignal` gains `kind` (`BRIGADE` | `RING` | `AGED_BRIGADE`, default `BRIGADE` for existing rows); unique becomes `(kind, nodeKind, nodeId, windowStart)`. One migration; `migrate diff` clean in CI.
- **Vote path:** `castVote` calls the detector on `APPLIED` and `GATED_DOWNVOTE` outcomes inside the caller's transaction, as D-31 does today.
- **Queue:** items `RING` ("Suspected upvote ring: N new accounts in 10 min") and `AGED_BRIGADE` ("Suspected brigade from accounts under 7 days: N downvotes in 10 min"), with the voters' handles and ages; reviewed through the existing `reviewSignal` (logged `REVIEW_SIGNAL`). Numbers in the copy are read from the rules file.
- **Eval:** `engine:eval` runs the detector over `fixtures/signals/` and diffs `expected_signals.csv`; `engine:eval:db` replays the scenarios through the real vote path and checks the rows.

## Non-goals

- Blocking, reversing, discounting or hiding any vote (D-31: a signal is for a human). Counts and Hot are unchanged by a signal.
- A classifier, IP/device fingerprinting, or cross-org correlation.
- Ban-evasion detection, report swarms, edit-after-votes (SME #5, #3, #7 — 5.4 or deferred).
- Changing the downvote gate, the young-account rule, or any rate window (D-73).
