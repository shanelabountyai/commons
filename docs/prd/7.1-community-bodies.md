# PRD 7.1 — Community bodies, organic reports and reposts: an additive fixture

**Status:** drafted 2026-11-04 (D-97); approved as drafted and built the same day (D-98). Governed by D-96 (Shane chose the fixture regeneration over closure), rule 8 (fixtures frozen; this PRD asks for one **additive** regeneration under D-97), D-10 (never edit an expected value to pass), D-31 (signals for humans) and non-negotiable 10 (say what the numbers mean). Size M, one PR. Builds on `phase-7.1` off `phase-6.4` (PRs #4–#11 still open).

## Problem

Four measurements have been carried since Phase 5 because the community fixture has no text:

| Carried item | Why it can't be measured today | Source |
|---|---|---|
| `min_contribution_chars` (three one-character replies pass the downvote gate) | No bodies, so no lengths | D-75 |
| Community reports raise no `REPORT_SWARM` | The community fixture holds 0 reports, so the check passes vacuously | D-81 |
| Link-host extraction (SME #8) | No bodies, so no hosts | D-92, D-93 (3) |
| Repost window (SME #9) | 0 repeated title or body by construction, so any window refuses 0 | D-92, D-93 (3) |

**`body_hash` is not a hash of any text.** `tools/build_fixtures.py:57,80` writes `sha256(id)[:16]`, and `src/forum/load.ts:51,62` writes the bodies `"<id> body"`. Real bodies can't match the stored hashes, so any regeneration either adds new files beside the old ones or rewrites `posts.csv` and `comments.csv`.

**The honesty problem, stated before anything is built.** The "normal side" of every measurement here will be text the author generated. A threshold calibrated against it measures the generator, not a homelab community. So the generator's rates are **fixed in this PRD, before any measurement**, and every number in `docs/EVAL.md` carries the line: *normal side = invented distribution (PRD 7.1 §1); a real community's rates are unknown.*

## Scope

### 1. Generator: `tools/build_community_text.py --seed 20261104` (new, stdlib only)

Reads `users.csv`, `boards.csv`, `posts.csv` and `comments.csv` **read-only** and draws from its own `random.Random(20261104)`, so `build_fixtures.py`'s stream and every existing file stay untouched. Writes three files under `fixtures/community/`:

- **`bodies.csv`** `node_id,title,body`: one row per post and comment (5,500). The rates below are fixed here (decision 2):
  - **Post bodies:** 200–1,500 chars, templated homelab Q&A and build logs (D-2 vocabulary).
  - **Comment bodies:** **8 % short** (2–20 chars, e.g. "+1", "Same here.", "Thanks, that fixed it"), the rest 40–600 chars.
  - **Links:** **15 % of posts and 5 % of comments** carry one markdown link, its host drawn from **12 fictional `.example` hosts** (RFC 2606), weighted toward docs and wikis. No real host appears.
  - **Organic reposts:** **2 % of posts (10)** are "wrong board" reposts: the same author, title and body as one of their earlier posts, on another board, 1–72 h later. These are the repost window's false-positive side. They are post pairs inside the existing 500, so no post is added.
  - Removed and deleted nodes get bodies too, so the loader stays total.
- **`reports.csv`** `reporter,node_id,reason,reported_at`: **1 report per 100 nodes (55)**. Reporters are drawn from accounts older than the node, reasons from `rules/moderation.json` `report_reasons` (weighted toward `spam`, `off_topic`, `duplicate`). Each removed node gets 1–3 extra reports (43 nodes). No coordinated group is scripted: this is the community side of the swarm check.
- **No pins** (decision 4).

### 2. Oracle

`tools/community_text_lib.py`: the normalized body hash (the TypeScript `bodyHash` rule, `src/forum/actions.ts:65`: lowercase, collapse whitespace, trim), host extraction from markdown links, length counts, and the duplicate and report-swarm checks over the new files. `tools/verify_fixtures.py` reproduces the three files byte for byte from the seed, as it does `expected_*.csv` today.

### 3. Loader

`loadForum` reads `fixtures/community/bodies.csv` for titles and bodies instead of `"<id> body"`, and sets `bodyHash` from the text (decision 3). The demo stops showing ids as text. Every value the expected files pin (order, counts, trees, pages, limits) is independent of body text, so `engine:eval` and `engine:eval:db` must stay at 0 differences unchanged. If either moves, that is a finding, not a fix.

### 4. Measurements: PRD 7.2, not here

7.1 builds the fixture and the oracle and stops. The four measurements, with the 6.4 bind test (attack allowed today, refused by the candidate, **0** community actions refused, non-vacuous), go in PRD 7.2, drafted after review. No rule value changes in 7.1.

## Non-goals

- Changing any existing fixture file, expected file or the `body_hash` column (it stays an opaque id hash; `bodies.csv` holds the text).
- Any limit, signal or rule value (PRD 7.2). Pins. Any classifier or host blocklist (D-31).
- A markdown, CSV or text library (stdlib only; the ask-before-add list is unchanged).
- Real hostnames, real handles or scraped text (D-1).

## Decisions this PRD asks of Shane (at review)

1. **Additive or rewrite.** **Rec: additive** (`fixtures/community/*` beside the frozen files). Nothing pinned moves, and the 19,611 rows stay comparable across phases. Alternative: rewrite `posts.csv` / `comments.csv` with bodies and real `body_hash`. That is truer to the schema, but it rehashes the base files every expected file is derived from, and a rule-8 exception that size needs its own review.
2. **The pre-registered rates** (8 % short comments; 15 % / 5 % links; 10 reposts; 1 report per 100 nodes). **Rec: as drafted.** They are plausible guesses, and what matters is that they are fixed before measuring. Alternative: name your own numbers now. They can't be tuned after 7.2 measures.
3. **The loader uses the bodies.** **Rec: yes.** The demo reads as a forum, and it proves the expected files don't depend on text. Alternative: fixture-only, leaving the loader on `"<id> body"`.
4. **Pins.** **Rec: none.** Pinning is a moderator action with no member path (D-92), and a pin cap calibrated against invented moderator behaviour measures nothing. Alternative: 0–2 pins per board in a `pins.csv`.
