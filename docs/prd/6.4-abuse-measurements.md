# PRD 6.4 — §C measurements: rules as data only where they bind

**Status:** drafted 2026-11-03 (D-92); awaiting Shane's review. Governed by D-59 (Phase 6 scope), D-31 (signals for humans, no classifier), D-10 (never edit an expected value to pass), rule 6 (constants are data) and rule 8 (fixtures frozen; this PRD asks for one additive regeneration of `fixtures/expected_limits.csv`, the 6.2 precedent, D-87). Size M, one PR. Builds on `phase-6.4` off `phase-6.3` (PRs #5–#10 still open).

## Problem

PO consolidation §C deferred five SME defenses as hypotheses: "measure in `abuse:*` first; rules-as-data when done" (`docs/reviews/2026-10-29-po-consolidation.md:50`, SME #4, #8, #9, #12). Today none is measured, so none can honestly become a limit (the 6.4 row's "must not": a limit nobody measured).

A read of the frozen community fixture for this draft (500 posts, 5,000 comments, 200 users; a stdlib script, numbers to be reproduced by the oracle in the build) splits them in two:

| Hypothesis | What the fixture can measure | Draft-time number |
|---|---|---|
| **Reply-chain flood**, window scope `profile+post` (SME #4) | Both sides: the attack is scripted; the normal side is every community comment grouped by (author, post) | Most comments by one author on one post: **3 in any 60 s, 3 in any hour, 5 in any day, 15 in total**. Today's per-profile window (6 / 60 s regular) allows **360 / h into one thread** |
| **`max_depth_written`** (SME #4) | Both sides: depth from the tree module's path | Community max depth **12**, p99 7; 53 comments sit past the render cut of 6. No cap on write today: a self-reply chain only meets the per-profile window, and the permalink page lists **every ancestor**, one line each (`src/app/o/[org]/f/p/[post]/c/[comment]/page.tsx:39`), so a 240-deep chain is a 240-line page |
| **Link-host extraction** (SME #8) | **Attack side only.** The community fixture stores `body_hash`, not bodies (the D-75 gap), so no host can be extracted and no false-positive rate exists | — |
| **Repost title-hash** (SME #9) | **Attack side only in effect.** Community (author, `title_hash`) pairs repeat **0** times and no `body_hash` repeats anywhere, so any window refuses 0 normal posts by construction (the generator writes unique text). The attack measures: the duplicate signal's window is 86,400 s (`rules/moderation.json`), so the same body reposted every 25 h raises nothing | 0 repeats |
| **Pin cap** (SME #12) | **Nothing.** The fixture holds no pins; pinning is a logged moderator action (`actOnThread`, `src/forum/moderation.ts:137`), not a member action | 0 pins |

So two measures can bind with both sides measured, and three cannot be calibrated on this fixture. The PRD measures all five and adds limits for the first two only, if the oracle confirms the numbers.

## Scope

**Bind test, written down before any number:** a candidate binds when (a) today's rules allow the scripted attack, (b) the candidate refuses it, and (c) it refuses **0** community actions. A candidate that fails (c), or whose (c) is vacuous, is recorded in `docs/EVAL.md` and does not become a limit.

### 1. Thread window: `scope: "profile+post"`

- **Rules.** Window rows in `rules/limits.json` gain an optional `scope`, `"profile"` (the default, so the five existing rows are unchanged) or `"profile+post"`. One new row: `{ "action": "comment", "scope": "profile+post", "per_seconds": 3600, "max": 10, "young_max": 3 }` (decision 1). Both comment rows apply; the first refusal wins, with its `retryAfter`.
- **Engine.** `checkLimit` stays pure and keeps its signature; the caller passes the history for the row's scope. The loader validates `scope`; `engine:lint` validates the file as today.
- **Store.** The `profile+post` history is the member's own `Comment` rows on that post (`authorId`, `postId`, `createdAt`): vote and comment rows are truth (rule 3), so no `LimitHit` column or migration. `submitComment` checks it after the existing `guardAndRecord`, inside the same transaction, and throws `RateLimited('comment', retryAfter)`.
- **Oracle first.** `tools/limitslib.py` gains the scoped check; `tools/reference_rank.py` writes two rows into `expected_limits.csv`:
  - `spam-flood-thread`: an aged, regular account (u050) replies to one post every 10 s for an hour, 360 attempts. Today: 360 allowed. Expected under the row: 10 allowed, 350 refused.
  - `normal-community-thread`: every community comment replayed through the thread row per (author, post), 5,000 attempts. Expected: 0 refused.

### 2. `max_depth_written`

- **Rules.** `"max_depth_written": 32` in `rules/limits.json`, next to `max_depth_rendered` 6 (decision 2): about 2.7 × the community max of 12.
- **Door.** The tree module computes the new comment's depth (rule 2, unchanged); `submitComment` refuses `INPUT_INVALID` "Too deep to reply here; reply higher in the thread" when it exceeds the rule, before `guardAndRecord`, so a refused reply spends no window slot. The thread page's reply link at that depth is not shown.
- **Oracle first.** Two more rows:
  - `spam-deep-chain`: one account self-replies a 60-deep chain at one per 400 s (inside the thread window). Expected: 32 allowed, 28 refused, `first_retry_after` empty.
  - `normal-community-depth`: the 5,000 community comments by depth. Expected: 0 refused.

### 3. Measured and recorded, not limits

`abuse:spam` gains three attack-only measures, printed and written to `docs/EVAL.md` §Phase 6 — 6.4, with no expected row and no rule:

- **Link hosts:** 20 posts by one account, each body with a different affiliate host and different wording. Prints what the duplicate signal raises (expected 0: no two bodies match). Extracting hosts is a 20-line function; a limit on them needs a normal side the fixture cannot give.
- **Repost:** the same title and body posted every 25 h for 7 days. Prints duplicate signals raised (expected 0 at `window_seconds` 86,400; 6 at 604,800). Widening the existing window is a one-value rule change the fixture cannot check for false positives (0 repeats by construction).
- **Pins:** none scripted. Recorded as "no member path; a moderator's pins are in the public mod log".

All three join the carried owner decision (`docs/phase-6-tasks.md`, D-75, D-81): one regeneration of the community fixture with bodies and organic reports would make link hosts, repost and `min_contribution_chars` measurable at once.

### The three copies of the limit scripts

The scripts live in `tools/reference_rank.py`, `scripts/abuse.ts` and `scripts/engine-eval-db.ts`. The first CI run of 6.2 failed because the third lacked the upload row (D-88). The four new rows go into all three in the same commit, and `engine:eval:db` is run locally before the push.

## Non-goals

- Any classifier, host blocklist, reputation score or ML signal (D-31).
- A limit for link hosts, repost or pins (section 3), and widening `duplicate.window_seconds`.
- Regenerating the community fixture (owner decision, carried). Any change to `src/render/`, the ranking rules, the moderation rules or an existing expected row.
- B7 edit integrity (stays deferred; this PRD does not measure late edits, because the fixture has no edit timestamps).

## Decisions this PRD asks of Shane (at review)

1. **Thread window:** 10 per hour per (member, post), young 3. **Rec: as drafted.** It is about 3 × the community max (3 / h), and a member answering questions in a busy help thread gets one reply every 6 minutes. The young value 3 sits on the community max, so if the oracle finds a young community member at 3 the row still passes; at 4 it fails the bind test and the value is raised under the same D- entry, not edited to pass. Alternatives: 6 / h (tighter, nearer the data), or measure and record only.
2. **Depth cap:** 32. **Rec: as drafted.** The permalink page cost grows by one line per ancestor, and 32 is 2.7 × the deepest community chain. Alternative: record only, since the thread window already slows a chain to 10 levels an hour.
3. **The three unmeasurable ones:** record them and fold them into the carried fixture decision. **Rec: record.** A host or repost limit with no normal side is the "limit nobody measured" the row forbids. Alternative: add a `REPOST` signal (a signal, not a refusal) with an attack-only fixture.
4. **Where the thread history comes from:** the member's `Comment` rows on the post. **Rec: Comment rows.** No migration, and the rows are already truth. Alternative: a `scopeId` column on `LimitHit` and a migration, which would also let a future `profile+post` vote row exist.
