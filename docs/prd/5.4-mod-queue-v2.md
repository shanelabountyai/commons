# PRD 5.4 — Mod queue triage v2

**Status:** draft for Shane's review, 2026-11-02. No code until approved. Governed by D-59; sequence approved by Shane (5.1, then 5.4). Size L; delivered as two parts on `phase-5` so each is reviewable alone.

## Problem

The queue (`src/app/o/[org]/f/mod/page.tsx`) lists up to 50 items (`rules/moderation.json` `queue.page_size`), each with its full body (up to 50,000 chars) and one form. Reviewers found (UX #9, design #5, SME §3 and #5, #12):

1. **Nothing to sort with.** No filter by kind (case / brigade / ring / aged brigade / duplicate) or by report reason; one long page.
2. **Acting means leaving.** A case offers remove / restore / clear only; warning or banning the author, or locking the thread, means going to another page and coming back.
3. **No reporter context.** The queue shows how many reported and why, and (since 4.1.14) what they wrote, but not who reported or how their past reports went — so a report-bombing campaign looks like a strong case.
4. **The log stops at 50.** No paging; targets are not links; `seq` (D-56) is not shown.
5. **Report swarms go unseen** (SME #5): five fresh accounts can open many cases against one member's posts in a day; each case is unique per node, so nothing connects them.
6. **A lock is half a lock** (SME #12): `THREAD_LOCKED` refuses replies only; votes and edits on a locked thread still go through.

## Part A — triage (UI and reads only; no new rules)

- **Compact rows:** kind badge (text), title link, author handle with state (ACTIVE / WARNED / BANNED) and their history counts, opened time with `<time>`, and the body as a 240-character excerpt in a `<details>` ("Show full text"), still through `Markdown`.
- **Filters as links:** `?kind=CASE|BRIGADE|RING|AGED_BRIGADE|DUPLICATE` and `?reason=<code>`; counts per kind beside each filter; the page size stays the rules file's 50, with `?page=`.
- **Act in place:** each case gets the author's warn / ban (duration from `ban_durations_hours`) / unban and the thread's lock / unlock, through the existing `moderateUser` and `moderateThread` actions, with a required reason; the redirect returns to the same filtered queue page.
- **Reporter context:** for each case, the reporters' handles, their account age, and their record so far — how many of their past reports ended `REMOVED` vs `CLEARED` (from the log; no new table).
- **Log:** paging (`?logPage=`), `seq` shown, target as a link to the node or the member.

## Part B — two rule changes, as data, fixture first

- **`REPORT_SWARM` signal** (signal only, D-31): ≥ `min_reporters` distinct reporters younger than `max_reporter_age_days` reporting nodes by the **same author** inside `window_seconds` → one queue item naming the target author and the reporters. Rules: `rules/moderation.json` `report_swarm { min_reporters: 4, window_seconds: 86400, max_reporter_age_days: 7 }` (proposed; set at review). Scenarios in `fixtures/moderation/scenarios.json` with an oracle `tools/modlib.py` and `expected_report_signals.csv` (swarm; organic reports from old accounts; three fresh reporters, one under threshold; one fresh account reporting many nodes — not a swarm, it is one reporter, and the existing 20/day report window covers it), hashed in the manifest; the community fixture untouched.
- **A lock locks:** a locked thread refuses votes and edits too (`THREAD_LOCKED`), with `rules/moderation.json` `lock_refuses: ["reply", "vote", "edit"]` so the set is data. Red tests first in `actions.test.ts`. Moderator actions (remove, restore) still work on a locked thread.

## Non-goals

- Automatic action of any kind (D-31), a classifier, reporter reputation scores that hide reports.
- Case assignment, claiming, appeals, two-person rules, per-board moderators (P2, PO pass §C).
- New roles (`Role` is template-owned; D-48).
- Phase 6 design tokens: badges here are plain text with the existing stylesheet.

## Acceptance

- **A:** e2e — the queue with ≥ 3 kinds present filters to each kind and back; a case's author is warned and the thread locked from the queue without leaving it, and both actions appear in the log with `seq`; the excerpt is ≤ 240 chars until expanded; reporter handles and their prior `REMOVED`/`CLEARED` counts show; log page 2 exists when there are > 50 entries. axe 0 light and dark on the filtered queue and at 320 px.
- **B:** oracle-written `expected_report_signals.csv` reproduced by `engine:eval` and by `engine:eval:db` through `submitReport`; the community's reports raise no `REPORT_SWARM`; `actions.test.ts` red then green for vote and edit on a locked thread; harness 14/14; full Playwright green in CI.

2. `report_swarm` thresholds: 4 reporters under 7 days in 24 h, as proposed, or others.
