# PRD 5.1 — Vote control: state, outcome, placement

**Status:** draft for Shane's review, 2026-11-01. No code until approved. Governed by D-59; sequence approved by Shane ("approve both recos": 5.1 next, then 5.4).

## Problem

Phase 4.1 made every vote answer with its outcome (`APPLIED`, `SWITCHED`, `TOGGLED_OFF`, `GATED_DOWNVOTE`, `SELF_VOTE`; 4.1.7). Three problems remain, raised by all three UI reviewers (UX #2, a11y S1/S6, design #2):

1. **No state.** The page never loads the viewer's own vote (`thread()` and `boardPosts()` in `src/forum/view.ts` read counts, not `Vote` rows), so ▲ looks the same whether you upvoted or not, and pressing it a second time silently removes the vote (V-3 toggle). Screen readers get no pressed state.
2. **Hidden.** ▲/▼ sit inside the per-comment `<details>` panel ("Reply, vote, report…"): one disclosure click per comment before you can vote. On the board page there is no vote control at all.
3. **The author's +1 reads as a choice.** D-12 fixes the author's +1, but on their own content the author sees the same live ▲/▼ and gets `SELF_VOTE` on press.

## Scope

- **Read the viewer's votes:** one query per page for the viewer's `Vote` rows on the nodes shown (thread: post + rendered comments; board: listed posts; permalink: the rendered rows) → a `myVote` map (`1 | -1 | 0`).
- **Placement:** a vote control to the left of each meta line, outside `<details>`, on the thread page (post and every comment), the permalink page and the board page (posts). The `<details>` panel keeps reply/report/edit/moderate.
- **State:** `aria-pressed="true"` on the button matching the viewer's vote; the visible glyph differs by state, not by colour alone (▲ / ▲ filled with a text label "upvoted"), so the state survives forced colours and greyscale.
- **Author:** on your own post or comment the control is replaced by text "+1 (yours, fixed)" — no buttons (D-12).
- **Outcome:** keep 4.1.7's `{notice}` with the outcome code; after an applied, switched or toggled vote the control shows the new state on the same response (`revalidatePath` already refreshes).
- **Targets:** ≥ 24 × 24 px each with a gap (WCAG 2.5.8; 4.1.13 set the minimum, this keeps it outside the panel).
- **Gated downvote:** for an account below the gate, ▼ stays enabled (pressing it records a `GATED_DOWNVOTE` event the brigade detector reads — D-31) and its accessible name says "Downvote (recorded, not counted until your account is 24 h old with 3 contributions)" from `rules/limits.json`.

## Non-goals

- Client-side JavaScript beyond server actions; optimistic updates.
- Any change to V-1..V-5, D-12, D-29 or the gate.
- Hiding scores, karma, or vote counts per user.
- Design tokens and the badge system (Phase 6, D-62).

## Acceptance

Red first, in this order:

- `view.test.ts` (new, DB): `myVotes(orgId, profileId, nodes)` returns 1 / −1 / 0 per node and nothing from another org (INV-03).
- e2e (new, in `e2e/commons.spec.ts`): on a thread a member presses ▲ on a comment without opening any panel → `aria-pressed="true"` and the notice `APPLIED`; presses ▲ again → `aria-pressed="false"`, `TOGGLED_OFF`; presses ▼ → ▼ pressed, `SWITCHED` (a mature member) or `GATED_DOWNVOTE` with ▲/▼ unpressed (a young one). The author's own comment shows "+1 (yours, fixed)" and no vote buttons. The board page shows a vote control per post with the same state. axe 0 in light and dark on thread, board and permalink, including after a vote and at 320 px.
- Vote buttons measure ≥ 24 × 24 px outside the panel.
- `npm test`, harness 14/14, full Playwright green in CI; `engine:eval` unchanged.

## Size

M. One session: one read function, one shared `VoteControl` server component used by three pages, CSS, tests.
