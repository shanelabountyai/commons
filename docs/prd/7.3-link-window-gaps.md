# PRD 7.3 — Close the link window's two gaps: what counts as a link, and edits

**Status:** drafted 2026-11-05 (D-103); approved the same day with all three review decisions as recommended (D-104). Governed by D-102 (fixtures for both attacks first, then the fix), D-100 / D-101 (the link window as built), D-32 (the edit mark), D-10 (never edit an expected value to pass), rule 7 (an abuse that works once becomes a fixture before it is fixed), rule 8 (fixtures frozen; this PRD asks for one additive regeneration of `fixtures/expected_limits.csv` plus a new `fixtures/links/`, the 6.2 / 6.4 / 7.2 precedent) and non-negotiable 10. Size M, one PR. Builds on `phase-7.3` off `phase-7.2` (PRs #4–#14 still open).

## Problem

PRD 7.2 put a `link` window on posts and comments: `{ link, 86400, max 5, young 2 }`. D-101 recorded two ways around it. Measured for this draft, the first gap is wider than D-101 says, and one detail of the second was wrong:

**1. The counter sees one link syntax out of eleven.** `linkHosts` (`src/limits/index.ts:93`) counts `](http(s)://…` only. Each body below was run through `renderMarkdown` and `linkHosts` for this draft:

| Syntax | Example | Renders an anchor | Counted today |
|---|---|---|---|
| inline | `[a](https://h)` | 1 | 1 |
| autolink | `<https://h>` | 1 | **0** |
| autolink, upper-case scheme | `<HTTPS://h>` | 1 | **0** |
| reference | `[a][r]` + `[r]: https://h` | 1 | **0** |
| collapsed reference | `[r][]` + definition | 1 | **0** |
| shortcut reference | `[r]` + definition | 1 | **0** |
| space before destination | `[a]( https://h)` | 1 | **0** |
| angle-bracket destination | `[a](<https://h>)` | 1 | **0** |
| upper-case scheme | `[a](HTTPS://h)` | 1 | **0** |
| newline before destination | `[a](⏎https://h)` | 1 | **0** |
| mailto | `[a](mailto:x@h)` | 1 | **0** |
| bare URL | `https://h` | 0 (`linkify: false`) | 0 |
| image | `![a](https://h/i.png)` | 0 (no images, D-40) | **1** |

Ten syntaxes put a clickable link on the page and ask nothing. The image is counted but never rendered as a link. The cause is the same in both directions: the counter guesses what the renderer will do, when it could ask the renderer.

**2. Edits ask nothing.** `submitEdit` (`src/forum/actions.ts:118`) goes through membership, the text checks and the lock, then writes. It has no limit. D-101 said links could be edited in "within 900 s". That is wrong: `edit_window_seconds` only decides whether the `edited` mark shows (D-32), so an author can edit at any time. Two attacks follow:
- **Edit-in:** post link-free bodies, then edit a link into each one.
- **Swap:** post 5 links, then keep editing them to new hosts. The window counts links at creation, so the count never goes up.

There is also a third problem, which the history causes. The window reads the links in the member's **current** body rows, timed at `createdAt` (`guardLinks`, `src/forum/limits-store.ts:53`). An edited-in link is timed at the post's creation, and a link edited out frees its slot. Body rows can't say when a link appeared.

**Today's numbers** (oracle `limitslib.replay_links`, account u050, the 7.2 timing):

| Script | Attempts | Today | Draft, after the fix |
|---|---|---|---|
| `spam-link-syntax-rotation`: 20 posts, one every 13 min, each with one link, using each of the ten uncounted syntaxes twice | 20 | **20 allowed** (0 links counted) | 5 allowed / 15 refused, first retry 82,500 s |
| `spam-link-edit-in`: 20 link-free posts, then 20 edits one minute apart, each adding one link | 20 edits | **20 allowed** | 5 / 15, first retry 86,100 s |
| `spam-link-edit-swap`: 5 one-link posts, then 15 hourly edits, each swapping the link for a new host | 20 | **20 allowed** | 5 posts allowed / 15 edits refused, first retry 82,500 s |
| `normal-community-links` (7.2 row, unchanged) | 325 | 325 / 0 | 325 / 0 |

**The community side:** `renderMarkdown` and `linkHosts` agree on all **5,500** community bodies: 325 linked, 325 anchors, 0 bodies differ, no images. So counting with the renderer leaves the 7.2 community row byte-identical. **The community fixture has no edits, so the edit half's community check is vacuous.** That cannot be fixed without regenerating `fixtures/community/`, which is a non-goal. The edit rule adds no constant: it asks the same window, with the same values, that a post with the same links would ask. *Normal side = invented distribution (PRD 7.1 §1); a real community's rates, edits included, are unknown.*

## Scope

### 1. Fixtures first (rule 7)

- **`fixtures/links/cases.json`**, written by a new `tools/build_link_fixtures.py` (stdlib, the `build_xss_fixtures.py` pattern). It holds the 13 rows of the table above, each with its body and the number of anchors it should render. These are the author's stated expectations, written before the counter, like the XSS set.
- **`python3 -I tools/reference_rank.py --write-expected`** adds the three `spam-link-*` rows above to `expected_limits.csv`. The attacks state their link counts by construction (one per body or edit), so the oracle needs no markdown parser. The thirteen existing rows stay byte-identical. `MANIFEST.json` lists and hashes the new file.

### 2. Count what renders (decision 1)

- **`linkHrefs(body)`** joins `src/render/` and replaces `linkHosts`. It is the only module allowed to call markdown-it (non-negotiable 1). It returns the href of every anchor `renderMarkdown` would emit, using the same parser instance, `flattenNesting` and `MAX_BODY_CHARS` cut, and the same `SAFE_HREF` test. `mailto:` counts, because it renders an anchor. Images don't, because they render none.
- **The pin:** for every `links/cases.json` row and every one of the 5,500 community bodies, `linkHrefs(body).length` equals the anchor count of `renderMarkdown(body)`. If the counter and the renderer ever drift apart, this test fails.
- `src/limits/` keeps `checkLinks` and `replayLinks`. They take a count, stay pure and unchanged, and lose `linkHosts`. `src/eval`, `scripts/abuse.ts` and `scripts/engine-eval-db.ts` call `linkHrefs`.

### 3. Edits ask the window (decision 2)

- An edit asks the `link` window once for each href in the new body that the old body does not have, counted as a multiset difference, at the edit's `at`. Keeping, removing or reordering links asks nothing. A swap asks for one slot. The young flag and `RateLimited('link', retryAfter)` work as they do on create, and the refusal text is the shared `refusalText`.
- `submitEdit` asks after `refuseIfLocked` and before `editNode`, in the same transaction, so a refused edit writes no `EditHistory` row.

### 4. History from recorded hits (decision 3)

- The `link` history moves to **`LimitHit` rows with `action: 'link'`**. An allowed create or edit records one row per new link at its `at`. A refusal records nothing (L-3). `LimitHit.action` is a `String`, so there is **no migration**. The sweep already keeps rows for the longest window.
- `guardLinks` reads those rows under the existing per-(profile, link) lock. Removing a link frees no slot, the same principle as 7.2 ("deleting frees no slot").
- **This reverses D-100 (4).** Body rows were chosen because they need no migration. Recorded hits need none either, and body rows can't place an edited-in link in time.

### 5. The three copies

The three new rows go into `tools/reference_rank.py`, `scripts/abuse.ts` and `scripts/engine-eval-db.ts` in one commit. In the two TypeScript copies the edit scripts run through `submitEdit`, which is the real edit path, and `engine:eval:db` is run locally before the push (D-88).

## Non-goals

- Any change to the window's values, the post or comment windows, or `edit_window_seconds`.
- A host blocklist or allowlist, per-host counting, or any classifier (D-31).
- Regenerating `fixtures/community/` to add edits, or changing any existing expected row.
- Turning on `linkify`, or any change to what `renderMarkdown` emits. The renderer is the reference; this PRD only reads it.
- A backfill of `link` hits for bodies posted before the deploy. Nothing is deployed, and the fixtures replay from empty.

## Decisions this PRD asks of Shane (at review)

1. **What counts as a link: every anchor the renderer emits, `mailto:` included.** **Rec: the renderer.** It closes all ten gaps and the image miscount with one source of truth, and a test pins it. Alternative: add only autolinks to the regex. That fixes the named finding and leaves eight syntaxes open.
2. **Edits: each href the edit adds asks the window, at edit time.** **Rec: as drafted.** It is the same rule a post with that link already meets, and it covers both edit-in and swap. Alternative: an edit may not add a link at all. That is simpler, but it refuses a member who fixes a broken URL. Under either choice the community side is vacuous.
3. **History: `LimitHit` rows (`action: 'link'`), reversing D-100 (4).** **Rec: LimitHit.** It needs no migration, it times an edited-in link correctly, and removing a link frees nothing. Alternative: keep body rows and rebuild each link's first appearance from `EditHistory`. That is more code on every check, and it reads the history from the content instead of from the record of actions.
