# Phase 3 — Hostility: XSS fixtures before the renderer, limits wired, abuse suites

Written at the Phase 2 gate (2026-10-29) for Shane's review. Not started. Phase 3 is the first time user text is rendered and the first time the limits engine is wired to storage. Exit bar: **the XSS fixture set renders inert through the real renderer; the spam-bot script is throttled by the stored limiter while the normal-user script is never refused; everything runs in CI.**

- [ ] **3.1 XSS fixture set, first.** `fixtures/xss/` (clone-owned, frozen, hashed in MANIFEST): script tags, event handlers, `javascript:` and `data:` URLs, SVG/MathML vectors, markdown link tricks, HTML entities, unicode confusables, nested markdown, oversize input, in every text field (title, body, handle, board title). Written **before** any renderer exists (non-negotiable 1). *Acceptance:* `python3 -I tools/verify_fixtures.py` covers them; each case names the field and the expected inert output class.
- [ ] **3.2 Sanitizer decision (stop and ask).** Propose the markdown + sanitizer pair with the reason (candidates: `markdown-it` + `DOMPurify`/`isomorphic-dompurify`, or `remark` + `rehype-sanitize`), the allowlisted subset (paragraphs, emphasis, code, links with `rel="nofollow ugc noopener"`, lists, blockquotes; no raw HTML, no images until 3.6), and the one module allowed to call it. **Do not add the dependency without Shane's yes** (ask-before-add list).
- [ ] **3.3 Renderer.** `src/render/` — the single sanitizer module; `npm run xss:check` runs every fixture through it and fails on any live vector. Output-encoded everywhere else; `dangerouslySetInnerHTML` only there (lint rule). *Acceptance:* `xss:check` OK; a planted `<script>` passthrough in a throwaway branch fails it.
- [ ] **3.4 Limits storage.** Wire `src/limits` to a store: proposed `LimitHit(profileId, action, at)` with an index and a sweep, giving a true sliding window (D-24); the foundation's `RateLimit` fixed-window counter is the alternative (C-4). The engine stays pure: the store supplies `history`, the engine decides. *Acceptance:* the Phase 1 limit scripts reproduce from the store; refusals return `retryAfter`.
- [ ] **3.5 Young-account gates wired.** `isYoung`/`downvoteAllowed` fed from Profile `joinedAt` + live contributions; `GATED_DOWNVOTE` already flows (Phase 2). *Acceptance:* a fixture brigade account cannot downvote; after 24 h and 3 contributions it can.
- [ ] ~~**3.6 Uploads.**~~ Moved to Phase 4 (D-40).
- [ ] **3.7 Abuse suites in CI.** `npm run abuse:spam` (a scripted young account: 60 comments/min, 20 posts/hour, 100 votes/min) and `npm run abuse:normal` (`u050`'s fixture activity replayed through the live store). *Acceptance:* spam allowed counts equal `expected_limits.csv`; normal refused = 0; both in CI.
- [ ] **3.8 Honest refusals.** Every refusal is a typed code with `retryAfter` where relevant, surfaced in the (Phase 4) UI and the API; no silent drops. *Acceptance:* a table of codes in `docs/domain-brief.md` and a test per code.
- [ ] **3.9 Phase 3 gate.** `docs/EVAL.md` §Phase 3; NEXT.md; `docs/phase-4-tasks.md` (reports with reason codes, mod queue with context, content and user state machines, append-only mod log, ban refusal `BANNED_UNTIL`, Handhold read first (D-19), pages and the seeded-community capstone demo) written and review requested.

**Decided (D-38..D-40):** sanitizer pair `markdown-it` + `isomorphic-dompurify`; limits storage = new `LimitHit` table; uploads deferred to Phase 4. **Nothing open before 3.1.** Phase 3 starts on Shane's go.
