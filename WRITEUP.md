# Commons — write-up: designing against the user you don't want

Build-log #16. A synthetic homelab community forum (boards, nested comments, Hot/Top/New/Best, one account one vote, rate limits, reports, a mod queue, an append-only log) built on saas-foundation v1.4.0 in four phases on 2026-10-29, cloud session, PR #1 against `main`, **not merged**. Numbers: `docs/EVAL.md`. Demo: `docs/DEMO.md`. Decisions: `docs/decisions.md`.

> Learning project, synthetic data only. Every user, board, post, comment, vote, report and moderation action is generated by `tools/build_fixtures.py` from a seed. Usernames are invented, emails use `example.com`, and nothing is scraped from a real forum. The spam, brigade and XSS fixtures are attacks this project's author thought of. Passing them shows the defenses stop those attacks; it does not show the forum is safe against attackers in general. Rankings use published formulas (log-scaled hot with time decay; the Wilson score lower bound) with constants in `rules/ranking.json`. They are not tuned on real engagement. Moderation is rule-based; no classifier judges content. Screens and write-ups report what was measured against the fixtures and never use "secure", "spam-proof" or "fair" without the number behind them.

## The angle

Every earlier project in the portfolio assumed its users wanted it to work. A forum's most active user is sometimes the one trying to break it. So the method here was: **write down the attacker before writing the feature**, turn each attack into a frozen fixture with an expected outcome computed by an independent Python oracle, and only then write the TypeScript that has to agree. The fixture set was generated once (`--seed 20261029`), hashed into a manifest, and never edited to make a test pass (D-10). The XSS cases were written in Phase 3 *before* the renderer existed, so the renderer was judged by a bar it had not seen.

Three design rules carried most of the weight, and each one found a bug when a shortcut would have hidden it:

1. **Counts are caches; event rows are truth.** Every vote is an event row, including the ones that don't count. A gated downvote is recorded and not applied; the brigade detector reads the rows the counter ignored. `votes:verify` recomputes every count from rows and must be clean.
2. **Engines are pure; `now` is a parameter.** `src/tree`, `src/ranking`, `src/votes`, `src/limits` import no database, clock, randomness or network; a lint enforces it. That is what made 19,568 oracle rows checkable in milliseconds, and what made "the same seed under Hot vs Top vs New at one instant" a table rather than a screenshot.
3. **One door, one writer, one renderer.** All user writes go through `src/forum/actions.ts`; only `src/forum/tree-write.ts` computes a path; only `src/render` may set HTML. The lint fails if any of the three is bypassed — and it did fail once, when the markdown wrappers were put in the wrong folder, which is the rule working.

## The attacks considered, and what stands in the way of each

Every row names the fixture or test that shows the defense holding. "Shows" means against that fixture; nothing more.

| Reaching another org's post by id | The template's invariants: cross-org ≡ not found, every secondary row scoped, no echo before authz; ten forum actions under the harness with five planted controls still turning it red | `inv-01-04-22-actions.test.ts` 14/14 |

## What the method cost, and what it bought

Stdlib-Python oracles, 18 fixture files under a manifest, and a rule that the TypeScript is written from the domain brief rather than ported from the Python. The cost was real: the fixture generator had to be corrected twice — about what a "live" XSS vector is (D-41) and about what markdown-it does past its nesting limit (D-42) — and each correction regenerated the fixtures under a decision entry rather than editing an expected file. No expected value was ever changed to make a test pass (D-10).

What it bought is the only claim this project makes: **every number in the demo was produced by a command you can run, against inputs that have not changed since they were generated.** 

## What it does not do, stated

No classifier reads content. No semantic search (Footnote's lesson; P1-4 is a plain `tsvector`). No deploy, no email, no storage beyond local disk. Hot and Best use reddit's historical constants, untuned, and whether they are good orderings for a homelab board was never measured. The brigade signal is a signal; nothing is auto-removed. An attacker who has read `rules/limits.json` knows exactly how many accounts they need, and this project does not pretend otherwise.

## Found while building (the honest list)

- **D-41:** the first "live XSS" patterns flagged entity-encoded text that could never execute. Fixed in the fixture before the renderer was judged.
- **D-42:** markdown-it drops content past its nesting limit silently; 500 nested quotes lost their text. Flatten first.
- **D-48:** the plan's "clone-owned Role value" was wrong on cost (the enum is template-owned). A Profile flag instead.
- **D-49:** an append-only log means the org that holds it cannot be deleted either. Kept, and the demo makes a fresh org per run.
- **D-53:** a NUL byte was inert on the page and a 500 in the database. The renderer check had not been enough; the browser run was.
- **D-46/D-54:** 15 `npm audit` advisories, 0 from this project, `next` at critical — the template's release to make.

Upstream to saas-foundation: `Role` and permissions need a documented clone extension point, or every clone that needs a role invents a flag.
