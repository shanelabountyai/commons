# PRD: Commons — Community Forum

**Sample business:** "Commons," a hobbyist forum for a homelab community (self-hosting, networking, home servers, small-board builds)
**Status:** v1.1 (2026-10-29). v1.0 (2026-09-25 draft, PM + community-moderator review baked in) plus the kickoff decisions in `docs/decisions.md`, which outranks this file.
**Build log:** #16, main track
**Learning objectives:** recursive tree data, ranking algorithms with time decay, vote integrity, moderation workflows, rate limiting. This is the first project designed against hostile users.

---

## ⚠️ Scope Honesty (read first)

Learning project, synthetic data only. Every user, board, post, comment, vote, report and moderation action is generated by `tools/build_fixtures.py` from a seed. Usernames are invented, emails use `example.com`, and nothing is scraped from a real forum. The spam, brigade and XSS fixtures are attacks this project's author thought of. Passing them shows the defenses stop those attacks; it does not show the forum is safe against attackers in general. Rankings use published formulas (log-scaled hot with time decay; the Wilson score lower bound) with constants in `rules/ranking.json`. They are not tuned on real engagement. Moderation is rule-based; no classifier judges content. Screens and write-ups report what was measured against the fixtures and never use "secure", "spam-proof" or "fair" without the number behind them. Keep this banner verbatim in the README.

## Problem Statement

A forum is a set of trees written by strangers. Comments nest arbitrarily deep, "what's good" is a ranking function that balances votes against recency, and some fraction of users are spammers, brigaders, or worse. Every earlier project assumes users act in good faith; this one assumes some won't. The lessons for the builder are **recursive data structures with honest query tradeoffs**, **ranking math**, and the change in mindset: **adversarial thinking as a design input**.

## Goals

1. Threads support arbitrary-depth nesting with efficient retrieval and sane pagination.
2. Hot/Top/New orderings are pure, tested functions, including comment ranking that stays honest on small samples.
3. One account = one vote, structurally; abuse is throttled by design, not by heroic moderation.
4. Moderators work from a queue with context, and every action is logged and reversible where possible.
5. **(Builder goal)** Tree storage strategy, ranking functions, defenses (rate limits, input hostility), moderation state machines.

## Non-Goals

- Real-time updates (polling, house rule), DMs, notifications beyond outbox stubs
- Federation/ActivityPub, mobile apps
- Karma economies (a visible count, no privileges economy — P2 seam)
- Image hosting beyond basic upload with size caps
- ML content moderation (rule-based defenses only; the seam for a classifier is noted)

## Requirements — Must-Have (P0)

**P0-1: Posts + nested comment trees** *(core learning artifact #1)*
Boards contain posts, and posts contain comments that nest arbitrarily deep. The storage strategy (materialized path or closure table) is chosen deliberately and the tradeoff is documented in `docs/adr-001-tree-storage.md`. Making that decision is part of the lesson.
- [ ] Fixtures: 8-deep nesting, mid-tree deletion rendering "[removed]" while preserving the subtree, author-delete vs. mod-remove distinguished
- [ ] Thread pagination: top-level comments page; deep branches truncate to "continue thread" links; a permalink renders any subtree with ancestors for context
- [ ] Retrieval cost measured: full-tree fetch for a 1,000-comment fixture thread timed and reported (Pulseboard's honest-measurement discipline)

**P0-2: Voting with integrity**
Up/down on posts and comments; one vote per user per item enforced by unique constraint; toggle (remove) and switch semantics.
- [ ] Self-vote policy explicit (author auto-upvote on create, non-removable — D-12)
- [ ] Vote counts denormalized for read speed but reconcilable: `votes:verify` recomputes from vote rows (derived-truth house rule)
- [ ] New-account gating: accounts younger than N hours or below N contributions cannot downvote (`rules/limits.json`). *Moderator review: the cheapest brigade defense there is*

**P0-3: Ranking functions** *(core learning artifact #2)*
Pure, fixture-tested: **Hot** (score with time decay: log-scaled votes against age), **Top** (windowed: day/week/all), **New**. Comments sort by **Best** by default, using the Wilson score lower bound, a confidence-adjusted ranking that doesn't let 2 votes with 1 up beat 100 votes with 70 up.
- [ ] Decay crossover fixtures: yesterday's 50-vote post vs. this hour's 5-vote post ordered correctly at multiple time offsets (GH-01..GH-04)
- [ ] Wilson fixtures cover the small-sample cases naive ratios get wrong (GW-01..GW-08)
- [ ] Rankings recompute via batch job (house convention) with freshness shown; formula constants live in `rules/ranking.json`, with the ADR explaining them

**P0-4: Rate limiting + input hostility** *(core learning artifact #3)*
Per-user, per-action sliding-window limits (posts/hour, comments/min, votes/min, reports/day), stricter for young accounts.
- [ ] A scripted spam-bot is throttled to negligible output while a scripted normal user never hits a limit (both suites in CI)
- [ ] All user content is hostile: output is encoded everywhere, markdown is limited to an allowlisted subset, links get `rel=nofollow`, and upload types and sizes are enforced. An XSS fixture set (script tags, event handlers and data URIs in every input) renders inert
- [ ] Limit responses are honest (retry-after), not silent drops

**P0-5: Reporting + moderation**
Users report with reason codes, which feed a mod queue showing the content in thread context, the reporter count and the author's history. Actions: remove (reason required), lock thread, ban (duration or permanent), and un-actions where reversible.
- [ ] Moderation state machine: content `visible → reported → removed | cleared`; users `active → warned → banned(until) → active`; all transitions logged with actor
- [ ] Banned users: posting rejected cleanly; existing content stays per policy (D-14)
- [ ] Mod action log is append-only and visible to admins (audit-log house pattern)

**P0-6: Edit windows + history**
Posts and comments can be edited during a window (config, default 15 min) without a mark; edits after that get an "edited" mark. Full edit history is stored and visible to mods.

## Nice-to-Have (P1)

- **P1-1:** Pinned/announcement posts per board
- **P1-2:** User pages: history, counts; block-user (hides content client-side)
- **P1-3:** Duplicate-content defense (hash recent posts; near-duplicate posts flagged to queue)
- **P1-4:** Search (title + body, plain full-text; the semantic, cited version is Footnote's lesson)

## Future Considerations (P2)

Karma-gated privileges · classifier hook in the report pipeline · shadow-ban mechanics (with the ethics note it deserves) · Pulseboard event integration.

## Success Metrics (seeded)

- Tree, ranking, and Wilson fixtures 100%; `votes:verify` clean
- XSS fixture set fully inert; spam-bot suite throttled, normal-user suite untouched
- A seeded community (200 users, 500 posts, 5k comments, scripted vote patterns + one brigade + one spam wave) ends with rankings matching hand-computed spot checks and the mod queue containing exactly the injected abuse
- Capstone: same seed data shown under Hot vs. Top vs. New side by side, then the spam-wave script running live into the throttles and queue

## Phasing (v1.1, D-6)

1. **Pure engines + oracle agreement, no database writes.** Tree module (path encoding, ordering, pagination, "continue thread" cut, removed-node rendering) and ranking functions (Hot, Top, New, Best) against the Python oracle and frozen fixtures; storage ADR decided with a measurement.
2. **Schema + votes.** Boards/posts/comments/votes/edit history in Postgres, one-vote constraint, denormalized counts with `votes:verify`, ranking batch job, the 1,000-comment retrieval timing.
3. **Hostility.** Rate limits, young-account gates, the XSS fixture suite *before* the renderer, upload limits, spam-bot and normal-user suites in CI.
4. **Moderation + UI + P1.** Reports, queue, state machines, mod log, edit windows, pages, seeded community, capstone demo.
