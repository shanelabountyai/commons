# Security audit: restaurant reservations (countertop-reserve)

- **Repo:** `/Users/shanelabounty/Projects/restaurant reservations`
- **Live:** https://reserve.labintelligence.co
- **Stack:** Next.js 16.3.3 (App Router, `middleware.ts`), React 19, Prisma 6 (`@prisma/client`) on Postgres, npm-workspaces monorepo (`apps/web`, `packages/core`, `packages/db`), Vercel with a cron job.
- **Exposure:** The whole site sits behind an HTTP Basic demo gate. The live site returns `401 WWW-Authenticate: Basic` on `/` and `/host`, checked 2026-09-23. `/host` also needs a shared staff passcode, which fails closed. Guests act only through 128-bit manage tokens. The two exempt API routes authenticate themselves: the webhook checks an HMAC and the cron route checks a bearer token. I found no anonymous path to guest data.

Method: I read the code; nothing was modified, built or run. The only network traffic was a few HEAD and GET requests to the live URL. Anything I did not confirm in code is marked UNVERIFIED.

## Gaps

| ID | Sev | Finding and exploit | Fix | Acceptance test |
|---|---|---|---|---|
| SEC-01 | MED | **Brute force on the staff passcode and demo password is unlimited.** `signIn` (`apps/web/app/host/login/actions.ts:8-27`) and `demoChallenge` (`apps/web/lib/demo-gate.ts:42-53`) count no attempts. The passcode is described as a "six-character word" (`staff-auth.ts:31-32`). Exploit: anyone holding the demo password (it is shared in demos) scripts POSTs to `/host/login` until the passcode falls, then sees guests' names and phones and can cancel tables. | Add a DB-backed attempt counter keyed by HMAC(IP) with lockout after N failures per window. Also enforce a minimum passcode length of 16 or more at boot. | Integration test: 11 wrong passcodes within 15 minutes from one address, then the correct passcode is refused with a throttled notice. A second address is unaffected. |
| SEC-02 | MED | **Staff session cannot be revoked and is password-equivalent.** The cookie value is `SHA-256("reserve-host:"+passcode)` (`staff-auth.ts:33-37`), identical for every device and every session. A leaked cookie (shared tablet, logs, a screenshot of devtools) grants `/host` until the passcode rotates. Rotating logs out every tablet. No logout path revokes anything server-side. | Issue random session ids stored hashed in a `StaffSession` table, with expiry and revoke, and check them in middleware through a DB lookup (or signed + watermark). Keep passcode entry as the login step. | Test: sign in on two "devices", revoke one session row, the revoked cookie gets 401 or a redirect and the other still works. A cookie value equal to the passcode digest alone is refused. |
| SEC-03 | LOW | **Manage tokens are stored in plaintext.** `Reservation.manageToken` (`schema.prisma:150`) is looked up by equality (`guest.ts:125,154`). A DB read (backup, analytics replica, support query) yields working links for every reservation, which can cancel or move them. There is also no expiry or re-issue. | Store `sha256(token)`, look up by hash, show the raw token only at creation. Add re-issue (host action) that rotates the hash. Send `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on `/m/*`. | Unit test: the DB row contains no substring of the issued token. The old token 404s after re-issue. A response header test on `/m/<token>`. |
| SEC-04 | LOW | **Demo gate fails open.** `demoChallenge` returns null when `DEMO_ACCESS_PASSWORD` is unset (`demo-gate.ts:39`), and the variable is not in `.env.example`. A redeploy or new environment that drops it makes booking and `/m` public (staff stays locked). This is the documented design (`docs/DEPLOYMENT.md:88`), but nothing stops a production deploy without it. | Fail closed when `VERCEL_ENV==='production'` (or `NODE_ENV==='production'` and not CI) and the variable is unset. Add it to `.env.example`. | Unit test: `demoChallenge('/', null, undefined)` in production mode returns 401 or 503. |
| SEC-05 | LOW | **No security headers.** There is no frame-ancestors or X-Frame-Options, so the `/host` floor (behind auth) can be framed for clickjacking of cancel or assign buttons. There is also no nosniff and no Referrer-Policy, so `/m/<token>` can leak through the Referer header if the page ever links out. Verified: `next.config.ts` has no `headers()`, and the live 401 shows only HSTS. | Add `headers()` in `next.config.ts`: `X-Frame-Options: DENY` / CSP `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (at least on `/m`), `strict-origin-when-cross-origin` elsewhere. | e2e: fetch `/`, `/host/login` and `/m/x`, and assert the four headers. |
| SEC-06 | LOW | **Webhook has no replay window.** The signature covers the body only (`inbound.ts:33-44`). A captured signed "X" (cancel) is harmless on replay thanks to the unique `providerMessageId` (`inbound.ts:144`). But a message the provider never sent cannot be forged, while an old one can be re-sent after the dedupe row is purged, if purging ever happens. UNVERIFIED whether InboundMessage rows are ever deleted; the trigger suggests they are not. | Sign `timestamp + "." + body`, reject if skew is over 5 minutes. | Unit test: a valid signature with a timestamp 10 minutes old gets 401. |
| SEC-07 | LOW | **Host actions rely only on the middleware.** No `requireStaff()` inside `move/assign/undo/ready/walkIn/edit` (`app/host/actions.ts`, `app/host/hours/actions.ts`). The code acknowledges this (`middleware.ts:12-15`). Next may route a server-action POST whose id is not in the current page's worker to another worker (UNVERIFIED for Next 16 on Vercel). A forwarded call would re-enter middleware, so I found no working bypass. The protection is one layer deep. | Add `await requireStaff()` (reads `cookies()`, calls `isStaff`) at the top of every exported host action. Add a lint or test that every `'use server'` export under `app/host` calls it. | Test: POST `Next-Action: <move id>` to `/book` without the cookie, and no reservation status changes. A source test that every host action export calls `requireStaff`. |
| SEC-08 | LOW | **Host header drives link origin.** `guestConfig()` builds `manageBaseUrl` from `Host` and `x-forwarded-proto` (`apps/web/lib/guest.ts:15-24`). On Vercel the Host is pinned to the project's domains, so this is not exploitable there (UNVERIFIED on other hosts). Off Vercel, a spoofed Host would put attacker links into confirmation texts. | Take the origin from an env var (`APP_BASE_URL`, falling back to `VERCEL_PROJECT_PRODUCTION_URL`), as the sibling clinic repo does. | Unit test: `guestConfig` with `Host: evil.test` still yields the configured origin. |

I found no IDOR. Guest surfaces accept only the token, and the DB layer re-reads it under `FOR UPDATE` (`packages/db/guest.ts:152-154`). Host surfaces are single-tenant. I found no raw-SQL injection sink (tagged `$queryRaw` only) and no `dangerouslySetInnerHTML`.
