# Security audit — alongside (handhold)

- **Repo:** `/Users/shanelabounty/Projects/alongside` (GitHub `shanelabountyai/handhold`, private per convention — UNVERIFIED visibility)
- **Deployed?** **Backend and apps: no.** `NEXT.md` (2026-09-23): status ON HOLD, "migrations … have not been applied to any real database", "no real email transport". No hosting config exists for `backend/`, `frontend/` or `admin-frontend/`. **Only the static marketing site `handhold-site/` is deployed** (Vercel git integration per `handhold-site/README.md:4`; waitlist via Formspree). The Vercel API listing returned no projects for the connected team, so the deploy is UNVERIFIED from the dashboard side.
- **Stack:** Fastify 5 + @fastify/jwt (HS256, one shared secret) + @fastify/rate-limit + argon2id (@node-rs/argon2) + Prisma 6 (Postgres / PGlite fallback). Two Vite React SPAs (consumer on :5173, admin on :5174) with a proxy to the API.
- **Exposure summary:** the auth design is careful: every private route has a preHandler, consumer tokens can be revoked through a tokenVersion watermark, and circle scoping is consistent. The gaps are in deploy hardening: the JWT secret silently falls back to a known default when `NODE_ENV` is unset, the 30-day refresh token sits in localStorage and is never rotated, rate limits are in memory, there are no security headers, admin roles are not enforced, and family invite tokens are stored in plaintext and written to the request log.

Method: read-only code reading. Nothing was built, run or tested. Where a claim depends on framework default behaviour rather than code in this repo, it says so.

## Gaps

| ID | Sev | Finding + exploit | Fix | Acceptance test |
|---|---|---|---|---|
| SEC-01 | HIGH (when deployed) | **JWT secret fails open.** `backend/src/config/env.ts:7-12`: `nodeEnv = process.env.NODE_ENV \|\| "development"`, and dev mode supplies a public default secret. Exploit: deploy with `NODE_ENV` unset or mistyped as `development`, and anyone can mint `{sub:<userId>, ver:0, typ:"access"}` with the string in the repo. They also get `{realm:"admin"}` tokens if they know an admin id. The server also falls back to ephemeral PGlite when `DATABASE_URL` is unset (`env.ts:50`). | Require `JWT_SECRET` (min 32) whenever `NODE_ENV !== "test"`. Refuse to boot if `JWT_SECRET` equals the dev default. Consider separate secrets for the admin and consumer realms. | Unit: `NODE_ENV` unset with no `JWT_SECRET` fails `env` parsing. `JWT_SECRET=dev-only-insecure-secret-change-me` with `NODE_ENV=production` also fails. |
| SEC-02 | MED | **30-day refresh token in localStorage, never rotated.** `frontend/src/api.ts:8-19` stores both tokens in localStorage. `/auth/refresh` (`backend/src/auth/routes.ts:113-133`) issues a new pair but the old refresh token stays valid for 30 days (`:28`). Exploit: one XSS, a malicious extension or shared-device access exfiltrates the refresh token, which keeps minting access tokens for 30 days. The victim sees nothing and nothing detects the reuse, until they change their password or sign out everywhere. No XSS sink was found (`markdown.tsx` escapes, no `dangerouslySetInnerHTML`), which is why this is MED. | Move the refresh token to an `HttpOnly; Secure; SameSite=Strict` cookie scoped to `/auth/refresh`. Make refresh single-use with a jti or family stored in the DB, and bump tokenVersion on reuse. | Test: redeeming the same refresh token twice gets a 401 on the second call, and the first pair is revoked too. The frontend never writes `handhold.refresh` to localStorage. |
| SEC-03 | MED | **Family invite tokens are plaintext at rest and never expire.** `prisma/schema.prisma:557` (`inviteToken String? @unique`, no expiry). They are written raw at `family/service.ts:110-118` and looked up raw at `:169-171,229,296`. Exploit: any DB read (backup, replica, support query, SQL-injection elsewhere) yields working links to join a circle. Links forwarded months ago still work. Admin invitations already fixed this (S-4, `admin/invitations.ts:8-30`). | Store `inviteTokenHash` plus `inviteExpiresAt` using the same helper as admin invites. Migrate existing rows by hashing them. | Test: a DB row never contains the raw token, and preview/accept with an expired token returns 404. |
| SEC-04 | MED | **Invite tokens logged through the URL path.** `GET /invitations/:token/preview`, `POST …/accept` and `…/decline` (`family/routes.ts:71-94`) put the credential in the path. The logger is enabled (`http/app.ts:76`), and Fastify's default "incoming request" log records `req.url`. `logging/redact.ts` redacts only object keys (framework default, not run). Exploit: anyone with log access (log vendor, ops) can harvest live invite links and join families. | Set `disableRequestLogging` or a custom `req` serializer that masks `/invitations/<token>`, or move the token into a POST body. Add `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex` on these routes. | Test: capture logger output during a preview request and assert the token substring is absent. Assert the three headers are present. |
| SEC-05 | MED | **Admin roles are not enforced.** `AdminRole` has `superadmin` and `support` (`admin_console/migration.sql:6`). `authenticateAdmin` sets `req.adminRole` (`http/app.ts:164`), but no route reads it (grep: the only use is `/admin/me`, `admin/routes.ts:196`). Exploit: a `support` admin can toggle feature flags (including `FEATURE_COMPANION`), execute erasures early, transfer circle ownership through succession, and sign safety copy. | Add `requireAdminRole("superadmin")` to flags, erasure-execute, succession-execute, signed-copy, billing and promo routes, following the mvp-G1 role table. | Test matrix: a `support` token gets 403 on each superadmin route and 200 on lookup/incidents. |
| SEC-06 | MED | **Rate limits are per process and per socket IP.** `@fastify/rate-limit` uses its default in-memory store (`http/app.ts:122`), and community limits use a module `Map` (`community/service.ts:31-32`). Exploit: with more than one instance, or after a restart, the 5-per-10-min admin-login and 8-per-10-min login limits multiply or reset, which enables credential stuffing. Behind a proxy with `trustProxy` unset, everyone shares one bucket (DoS on login; noted at `app.ts:115-121`). | Use a Redis or Postgres store for `@fastify/rate-limit` and move the community limiter onto it. Set `trustProxy` to the real hop count when deploying. Add a per-account failed-login counter. | Test with two app instances sharing a store: the 9th login across both returns 429. |
| SEC-07 | MED | **No security headers from the API, and no hosting config for the SPAs.** Only `x-content-type-options` is set (`http/app.ts:170-172`). Exploit: the admin console, once hosted, can be framed for clickjacking. There is no CSP to contain an XSS, and with tokens in localStorage (SEC-02) that combination is the whole session. | Register `@fastify/helmet` (HSTS, frame-ancestors 'none', Referrer-Policy). Ship CSP, HSTS and X-Frame-Options with whatever hosts `frontend/` and `admin-frontend/`, modelled on `handhold-site/vercel.json`. | Test: `inject('/health')` has HSTS, `x-frame-options`/CSP `frame-ancestors`, and `referrer-policy`. |
| SEC-08 | LOW | **Admin audit log is not append-only in the DB.** `AdminActionLog` protection is only a comment (`admin_console/migration.sql:2-4`). The same holds for the moderation actions that `SECURITY_REVIEW_COMMUNITY.md` calls append-only. Exploit: a compromised app role or a bad migration can rewrite the admin trail. | Add a migration with a `BEFORE UPDATE OR DELETE` trigger that raises an error (the pattern showcall uses) for `AdminActionLog`, the moderation actions table and `VaultAccessLog`. | Test: a raw `UPDATE "AdminActionLog"` throws. |
| SEC-09 | LOW | **In production, a missing email transport warns instead of failing.** `lib/email.ts:20-22`. Exploit or impact: signup returns 201 in prod and verification or invite mail silently never goes out. Users cannot verify, and addressed invites cannot be accepted (see `NEXT.md`). | Refuse to boot in production without an ESP configured. | Test: `buildApp` with `NODE_ENV=production` and no sender throws. |
| SEC-10 | LOW | **Timing-based account enumeration.** `auth/service.ts:150` returns before argon2 when the user is missing, and signup `:76-80` skips hashing on collision. Exploit: response time shows whether an email is registered, which reveals that a family is using a caregiving app. | Run `verifyPassword` against a dummy hash on the missing-user path, and hash on the collision path. | Test: missing-user and wrong-password login latencies are within the same band, or the dummy verify is asserted to be called. |
| SEC-11 | LOW | **Community moderators have no second factor.** `community/service.ts:708-725`: `staff_moderator`/`admin` globalRole on a password-only consumer account can read the mod queue, which holds crisis-triaged content, and can ban. | Require TOTP, or move moderation into the admin realm. | Test: a moderator without MFA gets 403 on `/community/mod/queue`. |
| SEC-12 | LOW | **Existence oracle (403 vs 404).** By-id services return 404 for a missing row and 403 "You are not part of this circle" for someone else's (`permissions/service.ts:23`, e.g. `care-log/service.ts:58` → `:135`). UUIDv4 ids make this hard to exploit. | Map `resolveMembership` failure on by-id loads to 404. | Test: GET another circle's `/care-log/:id` returns 404. |
| SEC-13 | LOW | **Unvalidated secondary ids.** `task.assignedToIds` accepts any user UUIDs (`task/service.ts:57,107`) without checking circle membership. Impact: a contributor-scoped task could be "assigned" to a non-member. No data is read through it. | Validate each id with `resolveMembership`. | Test: assigning a non-member id returns 400. |
| SEC-14 | LOW | **TOTP secrets are plaintext in the DB** (`"totpSecret" TEXT`, `admin/service.ts:38`). Anyone with a DB read can generate admin second factors; they would still need the password. | Encrypt with an app key held in the KMS or env. | Test: the stored value is not a valid base32 secret. |
